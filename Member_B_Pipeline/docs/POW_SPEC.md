# Proof-of-work challenge spec (stage 4)

Normative for the backend (`backend/app/defence/pow/`), Member C's simulator and Member D's solver.
Vectors: [`pow_vectors.json`](pow_vectors.json) (generated by `scripts/gen_pow_vectors.py` with plain
`hashlib`, independent of the implementation). Reference solvers: `scripts/pow_solver.py`,
`scripts/pow_solver.mjs`.

## 1. The rule

Find a **decimal-string** nonce `n` such that

```
SHA-256( utf8( prefix + ":" + n ) )   has at least  difficulty_bits  leading zero bits
```

`n` is written without sign, spaces or exponent: 1 to 20 ASCII digits (`[0-9]{1,20}`; anything else is
rejected before hashing). Leading zeros are allowed and are part of the hashed text (`"007"` and `"7"`
are different strings). Solvers search `0, 1, 2, …`; vectors give the **smallest** nonce, but the server
accepts any valid one. Leading zero bits are counted over the 256-bit big-endian digest.

## 2. Challenge object (inside `403 CHALLENGE_REQUIRED` → `details.challenge`, or `POST /defence/challenge`)

```json
{ "id": "fd1.p0.<event32>.<user32>.<exp>.<bits>.<nonce16>.<mac24>",
  "type": "pow",
  "expires_at": "2026-10-04T10:00:00.000Z",
  "pow": { "algo": "sha256-lzb", "prefix": "<same string as id>", "difficulty_bits": 14 } }
```
CAPTCHA challenges have `type: "captcha"` and `captcha: {provider, site_key}` instead of `pow`.
**The `id` is also the `prefix`.** The client submits `X-Challenge-Id: <id>` and
`X-Challenge-Solution: <nonce>` on a retry of the *identical* request (same body, same
`Idempotency-Key`).

## 3. Token format (stateless)

```
fd1 . <kind><pow_ok> . <event32> . <user32> . <exp> . <bits> . <nonce16> . <mac24>
```
| field | meaning |
|---|---|
| `kind` | `p` proof-of-work, `c` CAPTCHA |
| `pow_ok` | `1` = the PoW requirement is already satisfied (a CAPTCHA challenge issued after a solved PoW) |
| `event32`, `user32` | the event and user UUIDs as 32 hex digits: the challenge is bound to one person and one event |
| `exp` | expiry, Unix seconds (default lifetime 60 s for PoW, 120 s for CAPTCHA) |
| `bits` | required difficulty (0 for CAPTCHA); inside the MAC, so a client cannot ask for an easier puzzle |
| `nonce16` | 8 random bytes, so two challenges are never identical |
| `mac24` | first 96 bits of `HMAC-SHA256(key, "fd1\|<kind><pow_ok>\|<event32>\|<user32>\|<exp>\|<bits>\|<nonce16>")`, hex |

`key` = `POW_SECRET`, or `HMAC-SHA256(JWT_SECRET, "fairdrop/pow/v1")` when unset (domain-separated, so a
challenge can never be confused with a session token). Total length is 128–129 characters (**bounded**; D's B10).
Verification costs one HMAC and one SHA-256, with no database or Redis access.

## 4. Server decision table (`entry_gate`)

| presented | outcome |
|---|---|
| nothing, challenge required | `403 CHALLENGE_REQUIRED` with a fresh challenge (PoW first, then CAPTCHA) |
| malformed id, bad MAC, tampered field | **`403 REJECTED`** (hard evidence of tampering; the only reject in this stage) |
| valid MAC, issued to another user/event | fresh challenge (a replay is harmless, so no punishment) |
| expired | fresh challenge |
| wrong nonce / malformed nonce | fresh challenge (never a lockout) |
| already used (single-use, Redis `SET NX`) | fresh challenge. Best effort: Redis down ⇒ skipped, because replay is harmless anyway (bound to user and event; entry is idempotent) |
| valid PoW, CAPTCHA also required | `CHALLENGE_REQUIRED` with a CAPTCHA challenge whose id carries `pow_ok=1` (signed) |
| everything required is satisfied | `ALLOW` weight 1.0 (weights other than 1.0 arrive with the risk engine, stage 5) |

A client that solves correctly is therefore never refused; a bad actor learns nothing about *why* a
solution failed beyond "challenge again".

## 5. Difficulty

`bits = min(max_bits, base_bits + round(risk_bits_max·risk) + round(load_bits_max·load))`, monotone in `risk`
and `load` (tested over a grid). Defaults: `base_bits 14`, `risk_bits_max 6` (used from stage 5),
`load_bits_max 2`, `max_bits 24`, `load_ref_rps 200`. `load` = gate calls per second for the event over the last
complete second (cluster-wide, Redis counter) divided by `load_ref_rps`, capped at 1. Redis down ⇒ load 0.
The ceiling means no combination can price a legitimate device out.

## 6. Measured cost

Same machine, `scripts/pow_bench.ts` running **Member D's actual solver** (`pow.ts`) under Node/V8, 128-character
challenge prefixes, median of 7 challenges per row (a desktop CPU, **not a phone**):

| bits | expected hashes | median time | rate |
|---|---|---|---|
| 14 | 16,384 | 8.6 ms | 1.7 M/s |
| 16 | 65,536 | 39 ms | 2.1 M/s |
| 18 | 262,144 | 85 ms | 2.3 M/s |
| 20 | 1,048,576 | 418 ms | 2.3 M/s |
| 22 | 4,194,304 | 1.1 s | 2.2 M/s |

In real Chrome, through the whole flow (click → 403 → worker solves → retry → entered), a **20-bit** puzzle took
**≈1.9 s** (`scripts/browser_e2e.mjs`, one run, headless). D measured ≈1.2 M attempts/s in a browser worker; expect
a mid-range phone to be several times slower than this desktop: **run `/__dev/pow-bench` on a real phone before
choosing a production difficulty.** I have not measured a phone.
The default 14 bits costs a person ~10 ms on desktop and is invisible; it is the *adaptive* range (up to 24 bits
≈ 8 s desktop) that is perceptible, and only under load or (stage 5) high risk.

## 7. What it stops, and what it does NOT

**Stops:** unsolved requests (a bot must compute per entry); replaying one solution for another person; forging an
easier challenge; a request flood that skips the protocol.
**Does NOT stop:**
* A bot that simply solves it. At 14 bits a native solver needs ~1 ms per entry, so on its own the default PoW is
  nearly free for an attacker with CPUs; it only becomes real money at high bits × many identities. Its job is to
  add a *per-entry* cost, to let us raise that cost where risk or load is high, and to make "just hammer the
  endpoint" unprofitable. Member C's experiments must show its measured effect; if it has none, cut it.
* An attacker with many real, verified identities (software cannot).
* Solving ahead of time: a challenge is valid for 60 s and for one user, so pre-solving is bounded by that window.

**Cost to a legitimate user:** ~10 ms at 14 bits, automatic, no interaction, runs in a Web Worker (D's solver falls
back to the main thread if workers are blocked). Screen-reader users are unaffected (nothing to perceive).
Very old devices: capped at `max_bits`; if a device genuinely cannot finish, the CAPTCHA waiver does not help,
since PoW is not waived. Lower `base_bits`/`max_bits` for that event instead.

## 8. Test vectors

`pow_vectors.json` has `rule_vectors` (prefix, bits, smallest nonce, resulting digest) and `token_vectors` (fixed
key, event, user → exact token strings and, for PoW tokens, the smallest solution). Tests that consume them:
`test_pow_protocol.py` (rule, minimality, token round trip, every tamper), `test_reference_solvers.py` (Python and
JavaScript solvers agree with the vectors and with the backend), and a cross-check that **D's own vectors**
(`frontend/.../pow.vectors.ts`, from their independent Python tool) are all valid and minimal under this rule.
